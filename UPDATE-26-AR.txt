LARA STOCK — التحديث 26: تقليل طلبات الشبكة ونقل البيانات

النتيجة
عولجت نقاط تكرار مؤكدة في الكود قد تزيد استهلاك الشبكة. كل ميزات البوت والموقع السابقة باقية، بما فيها المدفوعات والسلة ومراقبة الأخطاء وبرودكاست القناة وروابط Mini App.
المقارنة تخص النسخة السابقة الموجودة من المشروع. لم تُراجع فاتورة حساب Render الفعلية، ولا تتوفر قياسات تشغيل شهرية تثبت سبب الفاتورة أو تضمن البقاء تحت 5 جيجابايت.

ما الذي كان يستهلك؟
1. المورد الذي تعمل واجهته من المسار الرئيسي كان يُكتشف من جديد في كل مزامنة؛ النجاح بمسار فارغ لم يكن يُحفظ. قد ينتج عن ذلك 8 طلبات بدل طلب واحد في كل دورة.
2. مزامنة المورد كانت تقرأ MongoDB لكل منتج على حدة، ثم تقرأ المجموعة مجددًا للمنتجات المفقودة؛ في عينة 150 منتجًا مستقرًا كان ذلك 151 قراءة من مجموعة منتجات المورد في الدورة.
3. ردود API للمنتجات كانت تُرسل كاملة دون ضغط أو استجابة شرطية عند عدم التغيير. الموقع كان يعيد إرسال قائمة المنتجات كاملة دوريًا حتى لو لم تتغير.
4. طابور إشعارات الأدمن كان يستعلم عند الخمول كل 3 ثوانٍ؛ بعض الإحالات كانت تكتب قيمة صفر الموجودة أصلًا في كل دورة. فحوص الإيداع كانت تعمل بوتيرة النشاط نفسها أثناء الخمول.
هذه أسباب محتملة من الكود، ولا تعني أن كل فاتورة سابقة سببها هذه النقاط وحدها.

التغييرات
- يُحفظ المسار الناجح للمورد، بما فيه المسار الرئيسي، فلا تعاد تجربة جميع المسارات في كل دورة.
- اكتشاف المسارات يستمر عند 404 فقط. أخطاء الصلاحيات أو الحظر المؤقت أو تعطل الخدمة لا تسبب تجربة بقية المسارات بلا فائدة.
- عند فشل المزامنة التلقائية يتدرج الانتظار: دقيقتان، 4، 8، 16، ثم 30 دقيقة كحد أقصى. تغيير إعدادات الاتصال أو المفتاح يعزل حالة الانتظار السابقة.
- المزامنة السليمة ما زالت كل دقيقتين؛ لا تُبطأ المتاجر السليمة. الفحص اليدوي والشراء لا يخضعان لانتظار فشل المزامنة الخلفية.
- إن دعم المورد ETag أو Last-Modified، تستخدمهما المزامنة التلقائية فقط لإعادة استخدام الكتالوج عند 304. الرد الفاشل لا يصفر المخزون.
- تُقرأ بيانات منتجات المورد دفعة واحدة مع إسقاط الوصف والبيانات الخام من قراءة المزامنة؛ وتقرأ قائمة انتظار المنتجات الجديدة مرة واحدة. تحديث السعر والمخزون والتوفر والإشعارات باقٍ.
- مخزون المنتجات العادية في API يحسب بتجميع واحد بدل عدّ منفصل لكل منتج، مع دعم أرقام المنتجات القديمة بصيغها الرقمية والنصية.
- كاش API مستقل لكل مستخدم وبمدة 30 ثانية وحدود للذاكرة. تعديل المنتجات أو أسعار وإخفاء مستخدم API يبطل الكاش؛ لا تتسرب الأسعار الخاصة بين المستخدمين.
- ردود JSON الكبيرة تُضغط بـ gzip إن كان العميل يدعمه. ما زالت كل الحقول والأوصاف والإيموجيات موجودة. العميل الذي لا يدعم الضغط يتلقى JSON عاديًا.
- يدعم كتالوج API الخاص استجابة 304 بواسطة If-None-Match بعد التوثيق وتحديد معدل الطلبات. يبقى الشراء بفحص السعر والمخزون من مساره الأصلي.
- الموقع يرسل رقم نسخة الكتالوج؛ عند عدم تغيّره يصل رد مختصر يحافظ على المنتجات المعروضة ويحدّث الرصيد وVIP.
- تحديثات الكتالوج المتزامنة في المتصفح تتشارك طلبًا واحدًا، مع مهلة 25 ثانية لتحرير الطلب المتعطل. التحديث الدوري يتوقف خارج تبويب المتجر أو عندما تكون الصفحة مخفية، ويعود عند الرجوع للمتجر.
- يُتفاوض على ضغط اتصال MongoDB بواسطة zlib عند دعم الخادم له، دون متطلبات مكتبة ضغط إضافية.
- عند عدم وجود إيداعات معلقة حية تصبح فحوص الإيداع كل 60 ثانية بدل 12. إنشاء إيداع يوقظ العمال مباشرة، ومع وجود إيداع معلق تبقى الوتيرة الأصلية 12 ثانية. تعذر قراءة قاعدة البيانات يبقي الوتيرة السريعة.
- الإيداع الذي يعتمد على ملاحظة Binance ولا يملك سجلًا معلقًا ما زال يُكتشف ضمن فحص الخمول؛ لا يلزم إنشاء طلب إيداع كي يعمل هذا المسار.
- طابور إشعارات الأدمن يفحص الاسترداد عند الخمول كل 30 ثانية بدل 3؛ إدخال إشعار جديد يوقظه فورًا.
- لا تكتب الإحالات left_checks=0 مجددًا إن كانت صفرًا؛ التحقق من الاشتراك والمكافآت باقٍ.
- لا يوجد حد شبكة يوقف البيع أو المدفوعات أو حذف لميزة بهدف خفض الاستهلاك.

زر القياس الجديد
لوحة أدمن البوت ← «📡 استهلاك الشبكة».
ويوجد كذلك في كونسول الموقع ضمن قسم النظام.
يعرض منذ بدء التشغيل عدد الطلبات والإرسال والاستقبال حسب: ردود الموقع وAPI، وجهات HTTP، اتصالات curl/ChatGPT، وأوامر MongoDB، مع أبرز المصادر وزر تحديث.
القياس لا ينشئ طلبات خارجية ولا يكتب سجلًا في MongoDB لكل طلب. يحتفظ بعدادات محدودة في الذاكرة، ولا يحفظ مفاتيح أو محتوى الطلبات أو روابطها الكاملة. يبدأ من الصفر بعد إعادة التشغيل.
الأحجام تقريبية؛ أحجام MongoDB قبل الضغط، وقد لا تتوفر أحجام بعض الردود المتدفقة. تكاليف TLS وبروتوكولات وخدمات أخرى ليست مشمولة. لذلك هذا الزر لتحديد المصدر، وليس بديلًا عن فاتورة الاستضافة.

نتائج المقارنة المحلية
- المورد بمسار رئيسي معروف: 8 طلبات HTTP قبل الإصلاح مقابل طلب واحد بعده في الدورة المستقرة؛ انخفاض 87.5% لهذه الحالة.
- مزامنة 150 منتجًا مستقرًا: 151 قراءة من مجموعة منتجات المورد مقابل قراءة واحدة. هذه ليست كل أوامر قاعدة البيانات في الدورة.
- عينة رد الموقع دون تغير الكتالوج: 8091 بايت كاملة مقابل 547 بايت للرد المختصر، قبل ضغط النقل.
- عينة JSON لاختبار الضغط: 86379 بايت قبل الضغط مقابل 571 بايت بعده. العينة تحتوي أوصافًا متكررة؛ هذه النسبة ليست توقعًا لحجم بيانات المتجر الفعلية.
- لا تمثل العينات تقديرًا للفاتورة الشهرية، ولا قياسًا على حسابات الإنتاج.

التحقق النهائي
- python -m py_compile bot.py: ناجح.
- 462 اختبار Python ناجحًا، منها 47 اختبارًا للشبكة والكاش والعزل والتراجع والفحوص المالية.
- فحص الأسماء غير المعرفة: صفر. فحص صياغة JavaScript: ناجح.
- Chromium حقيقي مع خادم محلي معزول: بقاء بطاقات المنتجات عند الرد المختصر، توقف تحديث الكتالوج على صفحة الحساب وعودته للمتجر، مشاركة الطلب المتزامن، دون أخطاء JavaScript أو شراء في اختبار الشبكة.
- فحص السلة في Chromium: الكمبيوتر والهاتف بوضع فاتح وداكن وRTL، الكميات وخصم الكمية، استرجاع نتيجة الشراء عند فقد الرد، استرجاع الإيصال بعد إعادة التحميل، الإلغاء الآمن، تعديل بريد الدعوة.
- جميع التعريفات السابقة محفوظة: 1206 تعريفات سابقة و1250 حالية عند احتساب الدوال الداخلية والكلاسات وطرقها بأسمائها المؤهلة؛ لا يوجد تعريف سابق مفقود.
- الاختبارات تستخدم بيانات وهمية وMongoDB في الذاكرة، وتمنع التكاملات الخارجية والاتصالات غير المحلية في خادم فحص المتصفح. لم تُنفذ مدفوعات أو رسائل قناة حقيقية.

بعد تثبيت النسخة
1. فك المجلد كاملًا، واحتفظ بإعداداتك الحالية. لا توجد متغيرات بيئة جديدة مطلوبة.
2. أعد تشغيل البوت مرة واحدة؛ لا تشغل نسختين بالخلفية في الوقت نفسه.
3. افتح Mini App من جديد ليحمل تعديلات الواجهة.
4. افتح «استهلاك الشبكة» بعد فترة تشغيل معتادة لتحديد المصدر الأكثر إرسالًا.
5. في Render: الخدمة ← Metrics ← Network Metrics ← Outbound Bandwidth. قارن HTTP Responses وService-Initiated. راجع الإجمالي الشهري في Billing.
Render يحسب حجم البيانات الصادرة، بما فيها ردود HTTP والاتصالات التي يبدأها الخادم؛ عدد الطلبات وحده لا يحدد حجم الاستهلاك. عدد العملاء والمنتجات والموردين والزيارات والبرودكاست يؤثر في الإجمالي. هدف 5 جيجابايت يحتاج متابعة القياس الفعلي بعد التشغيل.
